The one-page version

  1. The problem. When a UA business team has an idea for a tool, getting a working version means joining an engineering or analytics queue. Today that takes [baseline: median business days from request to first working prototype, measured in weeks 1 and 2] and [N] open EDMA requests are waiting. The context that would make the tool right is spread across functions and rarely in one room.
  2. Where it stands today. HyperDelivery, built in EDM, takes an idea through four AI agents and three human approvals to a working prototype. It works end to end on a laptop and is verified on AWS as far as the first approval. [N] projects have started and [N] teammates have used it. It has not yet run a measured pilot, and that is the first thing we fix.
  3. How we get there: three phases. Current State keeps today's EDM pilot running for its users while we measure a baseline and file every long-lead request in weeks 1 and 2. Final MVP builds to the new design until it is fully usable end to end (weeks 1 to 14): one assistant that hands Snowflake work to Cortex Code and coding to a sandboxed coding agent, projects that start from scratch, a Jira ticket or resources people point at, a per-project index of everything the project learns, and a new console, with friendly users from week 8. Then a real testing pilot (weeks 15 to 22): 8 to 12 users from at least three functions on real, low-risk work across a spread of use cases, in four two-week rounds. Enterprise (from week 23) adds governance, identity, logging and audit, cost and budget enforcement, evals, policy and HyperDelivery's own production environment, then more departments. A two-week do-no-harm floor keeps UA data and systems safe for pilot users; nothing in Enterprise is a precondition for the pilot, so the enterprise controls never hold the Final MVP back.
  4. Where HyperDelivery stops: at Inception. In UA-DLC, Ideation ends in a visual mockup, Inception in a working prototype (at most on a hosted sandbox, on dev data), Construction in a production-ready version on production data connections, and Operations runs the deployments and promotions after that. HyperDelivery's build stops at Inception: every project ends at its third approval with a handoff package (a Jira epic and issues, engineering's AI-DLC context files, the repository, the decisions and the evidence), built in the Final MVP. After Inception, UA decides per project, with a default set by risk, whether Construction is AI-driven or AI-assisted with engineers, because that is where work starts touching production systems and data.
  5. What we will prove in about 22 weeks. At least three projects reach an accepted working prototype and leave with a handoff package, at least four of five non-technical pilot users reach a working preview without help, at least half of pilot users start a second project, cycle time is measured against the week-2 baseline, and at least five distinct kinds of use case are tried. That is the pilot readout, with a stop rule if we miss.
  6. The smallest ask. Fund the Final MVP: the current owner, two borrowed engineers, part-time design and about two days a week from a data platform engineer, for about 22 weeks, about [cost]. Sponsor the requests with long lead times on day one (sandbox AWS account, Teams app, Microsoft Graph consents, prototype GitHub organization, Snowflake roles, a dev-data source from data platform, engineering's agreement on the handoff format, Brand review, an InfoSec heads-up) so Enterprise starts with approvals already moving. Enterprise waits for evidence at the pilot readout.
  7. What we will not build. No second data platform, no competitor to Snowflake CoWork (formerly Snowflake Intelligence), BI or Microsoft 365 Copilot, and nothing past Inception for now: HyperDelivery builds nothing on production data connections and deploys nothing to production, and Construction and Operations stay with UA's existing paths, decided after Inception. HyperDelivery is the governed path from idea to prototype on top of UA's Snowflake golden reports and Microsoft 365; section 5 shows which requests belong in other tools.

Part 1 - The narrative

1. Why now

At UA:

  • UA's data and AI investment now covers asking questions of data (Snowflake CoWork, the golden-report pattern) and developers writing code (Cortex Code, per the Snowflake case study, and GitHub Copilot, which UA job postings name). There is no governed path for a non-technical teammate to build something new with that data.
  • FY27 priorities create exactly these requests: another 25% SKU reduction within 18 months, fewer and bigger marketing stories with clear measurement, full-price selling and inventory discipline (Q1 FY27 call). Each needs a small analytic tool that several functions agree on.
  • The UA ideathon suggested that the best business context appears when technical and non-technical teammates from different functions work a problem together; the pilot tests this (section 3). Meeting tools such as Teams Facilitator capture notes, but nothing ties what such a room says to UA's data, definitions and owners and carries it into a build.

In the market, over the last eighteen months:

  • Writing code became cheap. Every major vendor ships a coding agent. UA job postings already name GitHub Copilot, and today's pilot builds with it; the plan moves building into a sandbox HyperDelivery controls (section 4). Factory's website lists Under Armour as a customer; we will confirm before the meeting what UA licenses and where it fits (section 5).
  • The slow part moved to intent, decisions and review. Anthropic's AI-native SDLC playbook, GitHub Next's Chopin and AWS's AI-DLC all make that case. Those are the steps where UA-specific knowledge lives.
  • Business-user app builders are churning. Microsoft is retiring its App Builder agent and vibe.powerapps.com on November 30, 2026 and moving app creation into Copilot Cowork's App skill (Frontier program only) and Apps in Copilot Studio (public preview) (MC1505609, Microsoft Learn). GitHub announced Spark's deprecation in August 2026. A platform that owns UA's process and stays neutral about where apps run is insulated from that churn. We carry our own exposure: several AWS services we plan to use became generally available in 2026, so the design keeps them behind replaceable interfaces.

2. Where HyperDelivery is today

This is the Current State phase, drawn as a diagram in section 9 (Phase 1: Current State). It stays as is for its current users while the Final MVP is built. Full detail with file references: current-state.md.

What works:

  • An idea goes through four AI agents (requirements, plan, build and review, demo) with three human approvals. The server re-checks every document rather than trusting the agent.
  • Approvals are signed by the verified Microsoft identity, can be undone for 12 seconds, and are kept as a trail.
  • A project can wait days for an approver without losing its place. All four agents are deployed on AWS in dev.
  • In local mode it reads Confluence, Jira, GitHub, Snowflake and S3 (Snowflake and S3 serve only the first agent), and builds with the GitHub Copilot coding agent, one change per group of work.
  • Every successful agent turn records its tokens and dollar cost.
  • The console is carefully built and accessible.

What is not ready:

  • Three workflow breaks on AWS: sending work back at any approval fails the run and strands the project, only the first agent can ask questions, and the demo step marks a project done on its own. Verified on AWS only as far as the first approval. There are also resilience defects (the Lambda that calls each agent times out at five minutes while a turn may run ten, with no retry or restart; full documents ride in the workflow's payload; lost updates) and review-scoring defects (a report with no requirement met can still pass).
  • The deployed setup is incomplete: the deploy script passes only the Snowflake settings, and only to the first agent, and the console API gets no GitHub token, storage bucket or Bedrock access. On AWS, uploads fail, the final approval's merge and build status are skipped without an error, and the first agent could not open an upload even with storage configured.
  • Security and operations: no roles or permissions, so anyone can approve their own request; everyone acts through one person's GitHub, Atlassian and Snowflake tokens, and the Snowflake token reaches the runtime as a plain environment variable, with no secrets store; some writes to GitHub and Jira happen before the approval that reviews them, guarded only by the prompt; the final approval squash-merges every build pull request with no check that its tests passed; anyone signed in can edit the instructions every agent reads; deletes are hard deletes with no audit, and the projects table has no point-in-time recovery; there is no dependency scanning; HyperDelivery runs only in dev, in one account and one region, with agent images pushed by hand and no release pipeline.
  • Data: the Snowflake integration asks for raw rows under a personal token and stores up to 1,500 characters of each result in its turn records. That breaks UA's "don't move data" tenet and is the first fix, inside the do-no-harm floor in weeks 1 and 2.
  • No hosted preview: the only preview runs the target repository's script on the same machine as the console API, so the working prototype effectively runs on a laptop.
  • Nobody is notified: the notification topic has no subscribers, so there is no Teams message, email or inbox; people find out by opening the console.
  • No memory: a fresh agent for every request, one shared notes field, and project files written to storage but never read; finished projects never feed back.
  • Not measured or tested: traces are created but never exported (the tracing setup has no exporter), logs are plain text keyed only by session, turn records are clipped to 1,500 characters, and cost is recorded only for successful turns, with no rollups. There are no evaluations, nothing has been usability-tested, and the pilot and baseline that the earlier plan (hyperdelivery-plan.md) set for around 18 October did not happen. The code is effectively one engineer's.

Bottom line. The core design is right and worth keeping: humans approve what passes between stations, the server checks the work, and each agent's permissions are separate from the shared integrations. The gaps are the normal gaps between a pilot and a platform. The Final MVP fixes the workflow breaks, and its do-no-harm floor closes the gaps that could hurt a pilot user in the first two weeks. The rest are platform gaps that the Enterprise phase closes once the pilot has shown what people use, so we harden the product people actually use rather than the one we guessed at.

4. The proposal: UA-DLC on HyperDelivery

UA-DLC, the Under Armour AI Delivery Lifecycle, is a four-phase line with three standing human approvals, and each phase is judged by what it hands over: Ideation a visual mockup that supplements the research and the brief, Inception a working prototype (at most on a hosted sandbox, on dev data), Construction a production-ready version on production data connections, and Operations the deployments, promotions and running that follow. Those outputs are the definition UA aligned on with [the other team] in October 2026. HyperDelivery runs the first two phases and ends every project at the third approval with a handoff package; Construction and Operations stay outside its build for now. The line keeps engineering's twelve steps (in AWS AI-DLC's vocabulary) word for word, in engineering's phases, adds Intake, Data discovery and a Mockup to Ideation and a sandbox prototype and the handoff to Inception, and names each approval by the decision it records:

The phase names are process vocabulary for the people who run the line; business teammates see Discover, Plan, Prototype and Handoff on the line, and approvals named by their decision ("what we're building", which signs the brief and the mockup together, "the plan" and "the working prototype"). The prototype stretch has its own step names (Prototype build, Checks, Evidence, Looks like the mockup, Try it), so Code, Review and QA keep one meaning: engineering's Construction work, in engineering's order. Construction and Operations are drawn dashed because they are outside HyperDelivery's build for now. This matches AWS AI-DLC 2.x, whose Ideation already ends in rough mockups and an approval (research). Every step's inputs, outputs, owner and screen are in operating-model.md. The line was checked against AWS AI-DLC, Anthropic's AI-native SDLC playbook, Microsoft's guidance (GitHub Spec Kit, Foundry and Copilot Studio) and software factories such as Factory, Runlayer and Chopin; the step-by-step comparison is in research/ua-dlc-reconcile.md.

Engineering has since built its own variant in UA's internal AI marketplace, for engineers in their coding tools, with gates of its own: a plan approved before any code, an explicit yes before a push or pull request, and every acceptance criterion checked in the running app. The two lines share a spine (no writes before approval, gaps recorded rather than guessed, a plan approved before code). HyperDelivery reuses engineering's contracts where they fit and hands work over in its format: its handoff lands where engineering's Construction tooling starts, with AI-DLC context files per ticket feeding engineering's Jira-to-PR pipeline, either with an engineer approving the plan (AI-assisted) or trusting approval 2 as the approved design (AI-driven), which engineering has to agree. What to settle with engineering is in operating-model.md (research).

A project can start anywhere people already are: a sentence typed from scratch, an existing Jira ticket with its linked pages, or resources people point at, such as a Teams recording, a OneDrive folder or a Confluence page. Nothing has to be uploaded. HyperDelivery reads what it is pointed at (Microsoft 365 files as the person who pointed, from the Final MVP; Jira and Confluence through an allowlisted service token until per-user sign-in arrives in the Enterprise phase) and indexes it for that project; that growing, cited, project-by-project memory of UA's own decisions is the moat (section 5).

Four rules make it UA's:

  1. Risk and the target tier decide who signs, never how many approvals there are. A low-risk "Prototype only" project needs only the requester. A T1 Team app target adds a business owner, a target that will read confidential data adds a data owner, and a T2 or T3 target, or high risk, adds an engineering reviewer from the intended receiving team (who signs).
  2. Every number cites a golden report or is labeled "uncertified". Snowflake stays the system of record for definitions; HyperDelivery creates no second semantic layer. On dev data the evidence says the definitions match and the numbers were not checked, rather than claiming the numbers match.
  3. Rows stay in Snowflake, and prototypes run on dev data. Snowflake work is handed to Cortex Code, which runs inside Snowflake and returns only schema, counts and aggregates, so data discovery can cite certified definitions without reading rows. Prototypes run in the sandbox on dev data (synthetic data, a dev Snowflake database, or views data platform designates as dev data), query live and keep no copies; the production runtime (Streamlit in Snowflake or engineering's platforms) is chosen and built in Construction.
  4. Questions go to the person who can answer them, in Teams, and the decisions people make are recorded with who made them and why.

HyperDelivery is the platform that runs UA-DLC: it already exists, and Part 2 says how it grows. The full process, including the prototype contract and target tiers, roles, time budgets and support, is in operating-model.md. (HyperDelivery's own phases, Current State, Final MVP and Enterprise, are in section 9; a project's prototype contract and its target tier, from T1 Team app to T3 Engineering-owned system, are in operating-model.md section 3. They are different things: a phase is how mature the platform is; a target tier is where one project's production version is meant to land, built in Construction.)

After Inception, UA makes the Construction decision. Every accepted prototype leaves with a handoff package, and the Construction owner (the receiving engineering lead, with the business owner) then chooses AI-driven (agents build the production version from the package), AI-assisted with engineers (engineers lead and may rebuild from the plan) or not now. It is a recorded decision, not a fourth approval. Its default comes from risk and the target tier, which is what the earlier "both, by risk tier" production path becomes: low-risk, read-only work with no sign-in or personal data defaults to AI-driven; sensitive data, authentication, writes to systems of record or core systems default to AI-assisted with engineers. Engineering's gates on push, merge and release apply in both modes, and a pipeline, never a model, deploys. AI-driven maps to engineering's jira-to-pr --require-context [confirm with engineering]. The package and the decision are in operating-model.md. Whether HyperDelivery later adds an AI-driven Construction lane of its own is decided at the scale decision, on handoff evidence; nothing is built for it before then.

How HyperDelivery does the work

From the Final MVP on, people talk to one assistant. Behind it, an orchestrator owns the conversation and the plan and hands work to specialists, each of which crosses one boundary per call and returns only what the project needs:

  • Snowflake work (finding the right tables, checking a metric against its certified definition, profiling, synthetic samples, drafting queries) goes to Cortex Code, which runs inside Snowflake under a scoped, read-only, per-task identity and returns schema, counts, aggregates and query ids, never rows.
  • Coding goes to a coding agent in HyperDelivery's sandbox, which builds the prototype on dev data: one Amazon Bedrock AgentCore harness session per build, in a sandbox AWS account that never runs HyperDelivery. It works through the signed plan's pieces in order with the whole plan in its workspace, tests after each piece, commits each one to a single branch, and asks a person when two readings of the plan would build different things. The engine is swappable behind one contract and the model is set per call (Claude Sonnet 5.5 through Bedrock). HyperDelivery, not the model, pushes and opens one pull request in a dedicated prototype organization, and the agent never holds UA data or credentials. GitHub Copilot's cloud agent, which turns each issue into its own pull request on autopilot, is not used for business prototypes; it stays acceptable on an engineering team's own repositories in Construction (research).
  • Resources people point at (Teams recordings, OneDrive and SharePoint files, Jira tickets, Confluence pages and their comments) go to a resource reader that reads them (Microsoft 365 as the person who pointed; Jira and Confluence through an allowlisted service token until the Enterprise phase) and indexes them into that project's knowledge base on AWS.
  • Checking goes to fresh-context reviewers and an evidence agent that runs every acceptance criterion in the sandbox prototype, so the author never grades its own work.
  • The handoff is assembled after approval 3: the Jira epic (for a T1 to T3 target) with an issue per ticket, engineering's AI-DLC context files (checked with engineering's own validator), the repository, the decision chain, the evidence, what the prototype skips, a dev-to-production data map and the target tier's Construction checklist. HyperDelivery records the Construction decision against it, and its work on the project ends there.

A small, trusted delegation broker sits between the orchestrator and every specialist: it scopes the credential for each call (service keys from Secrets Manager in the Final MVP; per-call minting for every system arrives in the Enterprise phase), caps the call's time and spend, validates what comes back against a typed contract, and writes the trace. Writes with side effects happen only after the human approval that authorizes them: the repository and the build after approval 2, the Jira epic and context files at the handoff, after approval 3.

The orchestrator stays on Strands, which the code already uses and AgentCore runs natively. LangGraph's main advantage, human-in-the-loop that resumes from saved checkpoints, already lives in Step Functions and the signed decision record, so we revisit it only on the triggers in platform-architecture.md. Step Functions stays as the spine that holds each project across days and parks it at every approval, with no model in that loop; LangGraph would replace Strands inside a step, not Step Functions (why). AWS's Strands Box sandbox is a v0.1.0 developer preview, so we watch it rather than adopt it, but its security lessons go into the threat model now: enforce outside the agent's process, never give the agent a secret, and give each credential domain its own sandbox (Strands Box and Dogwood).

The Final MVP's architecture is drawn in section 9 (Phase 2: Final MVP), beside the Current State and Enterprise diagrams. The full design, including identity at each step and what lands in which phase, is in platform-architecture.md. A project's Architecture tab shows that project's own solution architecture, while HyperDelivery's platform architecture lives in platform-architecture.md, on the plan page and on the concept canvas's Help page "How HyperDelivery Is Built".

5. Why HyperDelivery, and not a generic tool

Generic tools are good at building, and group work is starting to appear around them: Teams Facilitator captures meeting notes, and GitHub Next's Chopin (a research prototype) and Claude Tag (in Slack for Claude Team and Enterprise customers; Teams coming soon) are multiplayer. What none of them does is tie multi-party input to UA's data, definitions and owners, confirm it as reusable context, and carry it through signed approvals to a working prototype and a package engineering can build from. That makes HyperDelivery the best fit for one kind of request; for every other common request, another tool UA teammates can use wins or ties. The two matrices below show where each tool does its best work. The facts and their sources are in research/tool-landscape.md, checked on 2026-10-26.

Three names changed in 2026: Snowflake Intelligence is now Snowflake CoWork (Snowflake's own name, not a UA label), Cortex Code is now Snowflake CoCo, the same product renamed (this plan keeps the name Cortex Code), and Windsurf is now Devin Desktop. Cursor, part of SpaceX since August 14, 2026, keeps its name. Anything about UA's own licenses is marked [confirm].

How far it goes, and who builds. Across is how far the result goes: an answer (nothing is built), a personal tool one person runs, a team app hosted inside the tool that built it, or a path to production (code in UA's repositories with review, release and support, or a governed handoff to engineering for Construction). Up is who builds.

The bottom-right cell is the gap. Every tool that reaches a path to production expects an engineer at the keyboard, and every tool a business teammate can use alone stops at an answer, a personal tool or an app inside its vendor's platform. HyperDelivery is meant for that cell: a business teammate starts, and analysts, data owners and engineers join at its approvals.

Which tool for which request. Best fit is where we would send a typical request; Works means the tool can do it, with more effort or a caveat; Not for this means another tool should take it. HyperDelivery's marks describe the Final MVP, whose path to production is the handoff to Construction at the end of Inception; Construction itself is AI-driven or AI-assisted with engineers, decided per project.

Where each kind of request goes.

  • Snowflake. Simple questions about data go to Snowflake CoWork, which gives business teammates cited answers over certified semantic views without moving data. Snowflake's June 2026 announcement names Under Armour as a CoWork customer; who has it today, over which views, is [confirm]. An analyst's own dashboard goes to Snowsight, and a recurring dashboard on certified data goes to EDMA's BI team (Tableau or Power BI). Single-source Snowflake apps and pipelines, built by someone who writes code, go to Cortex Code with Streamlit in Snowflake, under the builder's own role [confirm who has it]. Data-quality checks stay with Snowflake Data Metric Functions and the existing observability tools.
  • Microsoft 365. Personal work on Microsoft 365 content goes to Microsoft 365 Copilot and Copilot Cowork, and simple team tools on Microsoft 365 data go to Copilot Studio, if UA licenses them [confirm]. Forms and simple workflows go to Power Automate, or Amazon Quick if licensed [confirm]. A recurring write-up from the same sources in the same format (a weekly report, a deal brief, variance commentary) becomes a shared skill and template in an enterprise assistant UA licenses; engineering's AI marketplace already runs scheduled briefings (research). Microsoft's business-user app building is still in Frontier or preview, and its App Builder agent retires on November 30, 2026, so "Best fit" for a team tracker is a forward-looking call.
  • Palantir Foundry and AIP. Operational apps where many people act on a shared object model, with write-back, go to Foundry and AIP, but only where the data already lives in Palantir's Ontology. For data that lives only in Snowflake, Palantir is not for this, given UA's stated "tenet of not moving data" (Chief Data and AI Officer, Snowflake case study). Whether UA licenses Foundry or AIP, and for which data, is [confirm]; no public source links UA to Palantir.
  • Engineering's coding agents. Changes, reviews and fixes in existing codebases go to GitHub Copilot, Factory (Droid), Claude Code or an agentic IDE such as Cursor, Devin Desktop or Kiro. They are close substitutes, so the choice follows what UA licenses and supports; UA's AI marketplace defaults to Factory and GitHub Copilot, and seats and plans for each are [confirm]. Large, multi-part engineering projects with an approved plan suit Factory or Claude Code. HyperDelivery's own coding agent stays behind the Builder port so it can follow whatever UA standardizes on, and a tool HyperDelivery prototyped is built in Construction with engineering's tools, AI-driven or AI-assisted.
  • HyperDelivery. A cross-functional new tool that a business teammate starts, that needs input from more than one function and more than one system, and that needs approvals, a record of decisions and a path to production comes here. It is for things people act in, not only look at: they enter assumptions, run scenarios, mark decisions, route approvals, or combine data with a workflow. It also works for the shapes the pilot will try: a data app, a team workflow tool, turning a report into an app, changing a tool its team already owns (as a pull request to that team), and a Teams-centered process. Engineering codebases stay with engineering's coding agents, and a simple Microsoft 365 tool still goes to Copilot Studio first. When a request fits better elsewhere, the person who runs the line says so in conversation; the product's screens carry no tool advice.

What HyperDelivery still has to prove. No other tool in the matrices combines all five: a non-technical person can start it; input from several functions is captured and attributed; numbers tie to UA's certified definitions; approvals scale with risk and record who decided and why; and the result can be handed to engineering as a complete package. Both halves of that cell, start to prototype and the handoff package, are now Final MVP work, and Construction itself is outside HyperDelivery, so the claim to prove at the pilot readout is that receiving engineering leads take handoffs into Construction without a rewrite. Until then the honest claim is that it is designed for the gap, not that it already fills it.

Hardening (weeks 23 to 36)

  • Identity and roles: Entra app roles with "assignment required", plus a default Contributor role so anyone can answer a question; approver relations and approval rules per target tier; reads on behalf of the user with a defined identity for each step; workspaces whose data owners pre-approve which confidential sources data discovery may profile (metadata and aggregates, never rows); strong sign-in (Entra authentication context) for High-risk approvals, changes to existing systems and the Construction decision.
  • No individual tokens anywhere: GitHub App installation tokens for every push and pull request, each valid one hour and limited to the named repository and permissions (no Copilot seat is needed, because the model never touches GitHub); Snowflake External OAuth per the reference design, with a per-task token for Cortex Code; per-user Atlassian sign-in through its remote MCP server, with a service account for gated writes; credentials minted per call by the broker for every system.
  • Logging and audit: structured logs; traces and the audit trail forwarded to UA's SIEM; hash-chained audit to S3 Object Lock; dashboards.
  • Cost and budget enforcement: cost per workspace with enforced budgets and alerts, and chargeback reporting; per-workspace Snowflake warehouses with resource monitors and statement timeouts; an Admin console for workspace guardrails and budgets.
  • Evals: golden sets for each station and specialist, model-quality evals, and contract conformance tests in CI (AgentCore Evaluations), with a floor a change must not drop below; the build conformance suite becomes a gate; on each model change, the golden intakes rerun with one harness component removed at a time, so parts that no longer help are retired (harness engineering).
  • Reviews, QA and testing: required security scanning on every generated repository, an accessibility check, the signed threat model, the InfoSec architecture review and the AI governance review.
  • Policy: AgentCore Policy on every agent tool call (Cedar plus Dogwood temporal rules such as "no push unless tests passed"), including Gateway policies on every coding-agent tool that writes, first in log-only mode, then enforced.
  • HyperDelivery in production: its own production environment with a release pipeline, a staging soak and tested restore; on-call, an SLO and a service desk category.
  • Construction intake: the risk engine reading Snowflake classification tags recommends the target tier and the default Construction mode; context files land where engineering's tools read them (a pull request to its AI-DLC repository, or attached to the Jira ticket) [confirm with engineering]; a repository transfers with a GitHub App token when Construction starts; and prototypes are cleaned up 30 days after the Construction decision. The handoff package itself is already built in the Final MVP.
  • The Library across projects: confirmed facts reusable across projects, built alongside Construction intake so the second department starts from what the first confirmed.

Enterprise ready criteria (week 36, proposed): per-user identity and dedicated roles live; no individual tokens anywhere (GitHub App installation tokens and service identities); golden and model-quality evals running in CI with a floor; security scanning required on every generated repository; structured logs forwarded to UA's SIEM; cost per workspace with enforced budgets and alerts; HyperDelivery's own production environment with tested restore, an SLO and on-call; InfoSec and AI governance reviews signed; a second department working in its own workspace.
