# UA-DLC site

A static site with the two things people ask to see: the UA-DLC plan as one readable page, and
every HyperDelivery concept screen on a pan-and-zoom canvas they can click through. No build step
and no framework; any static web server will do.

```
docs/ua-dlc/site/
  index.html              landing page: Read the Plan, Open the Concept Canvas
  plan/index.html         the rendered plan (generated by make site-plan; committed)
  plan/visuals/*.html     the plan's interactive visuals (sources)
  concepts/index.html     the canvas viewer (viewer.css, viewer.js)
  concepts/project/       the boards (*.dc.html), canvas.json, support.js, logos/
  variant-b/              the polished Variant B screens, source of the Figma file (its README)
```

Every name, project and number in the concepts is invented to show the design; none is a
measured result.

## Open it

```bash
make site
```

That runs `scripts/serve_ua_dlc_site.py`, which serves this folder at <http://localhost:8766/>
(`--port` changes it): the plan at `/plan/` and the canvas at `/concepts/`. It listens on this
machine only (`127.0.0.1`), because the site is a draft. Any static server works, for example
`python3 -m http.server --bind 127.0.0.1 --directory docs/ua-dlc/site 8766`, but its log fills
with 404s for `{{...}}` paths (see "Known console messages").

Opening the files directly (`file://`) works for the landing page and the plan, and their links
land on pages (they point at `index.html`, not at folders). The canvas itself needs the server:
the viewer reads `concepts/project/canvas.json`, and browsers block that read from a file page
(tested in Chrome, which shows a short message pointing back to `make site`). Each board also
opens on its own from `concepts/project/<Board>.dc.html` when served.

## Use the canvas

| To | Do this |
|---|---|
| Pan | Drag the empty canvas, hold Space and drag anywhere, or scroll with two fingers |
| Zoom | Ctrl or Cmd and scroll, pinch, the + and - buttons or keys |
| Switch page | Click a page in the bar's page switcher, or press 1 to 9 (arrow keys move through the pages while the switcher has focus); the view stays where it is |
| See everything | Fit All, or Shift+1 (the canvas opens on the first boards of the first row) |
| Frame the selected board | Fit Board, or Shift+2; Shift+0 zooms to 100% |
| Go to a board | Click it in the board list, or use the arrow keys or `[` and `]`; both cover the current page |
| Use a board | Double-click it, or press Enter; it zooms to fit, takes clicks and typing, and scrolls when it grows past its frame |
| Follow a link to another board | Click it as usual; the viewer moves to that board, and a link to part of a board (`Inbox.dc.html#q`, an Inbox item) opens it on that part |
| Back to the canvas | Esc, or Back to Canvas. A board's open menu or a text field takes the first Esc (the menu closes and focus returns to its button); the next Esc leaves the board |
| Open a board full page | Open on the board's title strip, or in the bar at the bottom while using it |

The address bar remembers the board in use (for example `/concepts/#Start`), so a link opens
straight on that board. On a canvas with pages it also remembers the page: `#b/Start` is the
`Start` board in use on page `b`, `#a/` is page `a` with no board in use, and the opening page
with no board in use has no hash. A bare `#Start` still works and opens on the page that holds
`Start`.

Pages hold alternatives of the same screens: switching pages keeps the view, so a board drawn at
the same place on another page appears in place, and the board in use or selected hands over to
it. Only when nothing of the new page is in view does the canvas move to that page's opening
view. Number keys switch pages while the canvas or the viewer's controls have keyboard focus; a
board in use keeps its own keys, so click the switcher there.

Boards load only when they are on screen at a readable zoom (about 15% or more), and the viewer
unloads far-off boards once more than about eight are live, so a long session stays light; a
board on another page counts as off screen but stays loaded while there is room, so switching
back is instant. A board ignores the pointer until you use it, which keeps dragging and scrolling
on the canvas. While a board is in use the board list steps aside so the board gets the full
width, and comes back on Esc.

The viewer reads everything from `concepts/project/canvas.json`: each board's `x`, `y`, `w`, `h`
and `title`, the `title1` notes as row titles and board-list groups, and `order` for the arrow
keys. An optional `pages` list (`{"id", "name"}` in switcher order; ids are letters, digits, `-`
and `_`) adds pages: a board or note with a `page` id sits on that page, and one with none sits
on the first. `launch.page` picks the page the canvas opens on (otherwise the first). With no
`pages`, or only one, the canvas has no switcher and works as one page. A title reads
`Name · Sub · Phase`: the phase (`Final MVP` or `Enterprise`) shows as a tag, and a note in
parentheses after it joins the sub line. A `title1` note that heads no boards (the "invented"
disclaimer) shows as a caption on its page and at the foot of the board list; a page that should
carry it needs its own copy. Add or move a board there and reload.

### Known console messages

The canvas runtime renders each board from its template only after the browser has parsed that
template as live HTML, so every bound image (`<img src="{{logos.teams}}">`) is requested once
with its raw `{{...}}` placeholder. `make site` answers those placeholder requests with an empty
image and leaves them out of its log; a real missing file still gets a 404 and is logged. A plain
static server answers each placeholder with a 404 instead, and the board's inline `onError`
handler then logs an "is not defined" error.

Either way the browser console still shows SVG attribute errors for `d`, `points`, `cx` and `cy`,
and `[dc-runtime]` warnings about values that "never resolved", from the same early parse. They
are harmless: the rendered boards are correct. They come from inside each board's frame and the
vendored runtime, so neither the viewer nor the server can silence them.

## Rebuild the plan

```bash
make site-plan
```

This runs `scripts/build_ua_dlc_plan.py`, which needs [pandoc](https://pandoc.org/) on the PATH
(`brew install pandoc`). It renders `docs/ua-dlc/enterprise-plan.md`, the source of truth, into
`plan/index.html`, light only, and swaps each visual marker for its fragment in `plan/visuals/`:

- `<!-- plan-visual: NAME -->` ... `<!-- /plan-visual -->` replaces everything between the
  markers (a mermaid block or a table) with `plan/visuals/NAME.html`;
- `<!-- plan-visual: NAME -->` with no close marker replaces the one mermaid block after it.

GitHub shows the fallbacks; the page shows the visuals. A missing fragment keeps its fallback
and prints a warning, and any mermaid block left on the page renders in the browser. Links to
companion documents open the repository on GitHub. Rebuild after editing the plan or a visual,
and commit the result.

Options:

- `--out` writes the page somewhere else.
- `--concepts-href` changes where "Open the Concept Canvas" points (default
  `../concepts/index.html`). While it is relative (the site build), the plan's own links to the
  claude.ai canvas and plan page point at this site instead: the canvas, the canvas on the
  `PlatformArchitecture` board for "How HyperDelivery Is Built", and the plan's Final MVP section.
- `--home-href` changes where the masthead lockup points (default `../index.html` for the site
  build, no link when `--concepts-href` is a URL).
- `--repo-ref` is the branch or tag companion-document links open on GitHub (default `dev`).

The roadmap's gantt rows live in `scripts/ua_dlc_gantt.py`;
`uv run python scripts/ua_dlc_gantt.py` prints the mermaid block to paste under the roadmap
marker.

## The claude.ai copy

The boards here are the source. The shared claude.ai canvas is published from this folder:
the boards and `canvas.json` are copied as they are, with each `logos/<name>.svg` path rewritten
to the matching asset uploaded to that artifact. The claude.ai plan page is built with the same
script, passing `--out` and the claude.ai canvas URL as `--concepts-href`, which keeps the plan's
claude.ai links as written. Edit boards here, then republish; never edit the claude.ai copy
directly.

## Vendored files

- `concepts/project/support.js` is the canvas runtime that renders the `*.dc.html` boards: the
  Design artifact type's `dc-runtime.js`, bundling React 18.3.1 (MIT license, notice kept at the
  top of the file), copied 2026-10-26. Do not edit it by hand; copy a newer runtime over it.
- `concepts/project/logos/` holds third-party product marks used on the boards to name the
  systems they show.

Both, and the generated `plan/index.html` (its source, `enterprise-plan.md`, is checked), are in
`cspell.json`'s `ignorePaths`. The boards and the plan visuals stay in the spelling gate.
