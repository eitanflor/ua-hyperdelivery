# Software factories, 2025-2026: landscape, mechanisms to adopt, and HyperDelivery's moat

*Researched 2026-10-25. Vendor claims are self-reported unless noted. Items marked (secondary) come from third-party write-ups that I could not check against a primary source.*

## 1. What "software factory" means now

By late 2026 the term has settled. A coding agent on its own is not a factory. The factory is everything around it: the signals that feed work in, isolated sandboxes, the loops that keep agents going, and the gates that check output before it ships ([awesome-software-factories](https://github.com/varun1505/awesome-software-factories)). Dan Shapiro's five-level scale ([Jan 2026](https://danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)) put "dark factory" at level 5: nobody reads the diff. Addy Osmani's [light vs dark](https://addyosmani.com/blog/software-factories/) framing is the useful one for UA. The real constraint is **verification, not generation**. Autonomy should go no further than you can cheaply verify. Auth, billing, public contracts and big-blast-radius changes stay "lit", and dark factories build up *comprehension debt* while the tests stay green. StrongDM runs a true dark factory: humans don't write or review code, and validation uses LLM-judged scenarios plus a "Digital Twin Universe" of cloned SaaS APIs ([factory.strongdm.ai](https://factory.strongdm.ai/)). Most serious operators run light factories. Stripe's Minions merge more than 1,000 agent-written PRs a week, and every one is still human-reviewed ([Stripe, Feb 2026](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)). The skeptics also have a point. One review of 21 company write-ups argues they are all "parallel agents on the process the company already had" ([Mitchem](https://medium.com/@NMitchem/nobody-has-actually-built-a-software-factory-77ffdc0c3efc)).

**HyperDelivery is a light factory by design.** Its four gates are the "lit" switches. The open question is which other loops can safely run dark.

## 2. The Runlayer reference factory (Oct 13, 2026)

Rafal Wilinski (founding engineer at Runlayer, formerly AI agents lead at Zapier) described Runlayer's internal factory in an [X post](https://x.com/rafalwilinski/status/2109940991868252302), fetched via [fxtwitter](https://api.fxtwitter.com/rafalwilinski/status/2109940991868252302). It had about 30k views and 700 bookmarks. It is a single post with no thread or quoted post. It includes a 41-second video I could not watch. The core idea is that shipping need not "start with your prompt or end with merging to main." The pipeline:

1. **Signals from many sources.** Customer calls (via Fireflies), customer Slack channels and red CI on main all start work. So do @-mentions, DMs, and a pin dropped on any UI element, in production, using Agentation. The element, the page and the note go to a webhook, which starts an agent.
2. **Dedupe before work.** Every ask is checked against Linear and open PRs. If the work is already tracked, the customer is added to the existing issue "as one more voice" rather than getting a new ticket.
3. **Risk routing.** Small, clear work is built immediately. Anything bigger, or near auth or hot paths, goes to the relevant engineers as a short write-up or draft PR.
4. **Sandboxed build with evidence.** The agent clones the repo, reproduces the bug, fixes it and runs the tests. It opens a PR with before/after screenshots, or a recorded walkthrough for bigger changes, so nobody has to check out the branch.
5. **Adversarial review and tiered auto-merge.** A second agent reviews adversarially. Small, non-risky changes are approved and auto-merged.
6. **PR babysitting.** When the reviewer or CI pushes back, an agent answers every comment. It fixes what is real, argues with what isn't, fixes red CI and conflicts, then asks for review again. Humans step in only when asked.
7. **After merge.** A QA fuzzing agent probes production. The people who care (FDEs, the salesperson who promised the feature, the customer who reported the bug) get a DM.
8. **Internal enablement.** One agent merged 91 PRs in 24 hours, so internal awareness became the bottleneck. Two fixes: an append-only changelog ledger (one markdown file per PR), and a weekly 3-minute video digest of the top 10 changes, presented by an AI persona.

**[Agentation](https://www.agentation.com/)** (v3.1.2, about 23.6M npm downloads, free for internal use) is a dev-dependency toolbar. You click any element and write a note. It outputs the CSS selector, source file path, React component tree, computed styles and your note as markdown. It also offers an MCP server and an [annotation schema](https://www.agentation.com/schema), so agents can list, question and resolve annotations, plus webhooks with auto-send. OpenAI shipped the same idea at DevDay 2026: a [Browser Annotation API](https://learn.chatgpt.com/docs/annotations-extensibility.md) (`document.oai.annotation`) that sends page selections to Codex. Copilot Studio's app builder lets makers [annotate the app canvas](https://learn.microsoft.com/en-us/microsoft-copilot-studio/apps-experience/create-app) to point at what should change. **Point-and-say feedback on a running app is becoming the standard input for non-technical users.**

**Runlayer the product** ([site](https://www.runlayer.com/), [llms.txt](https://www.runlayer.com/llms.txt)) is not a coding tool. It is an "AI control plane": an MCP gateway (200+ servers), a catalog of skills and plugins, shadow-AI discovery, and runtime security that scans tool calls in 50-100 ms. [Runlayer Agents](https://www.runlayer.com/agents) are provisioned with exactly the connectors and scopes of the employee who launches them ("if a human can't do it, neither should an agent"). They run from Slack, schedules or webhooks, and the platform "turns traces and execution history into improvements" to prompts, triggers and model choice. The pitch is "the golden path" for every employee. That is the same phrase UA would use for HyperDelivery.

## 5. Mechanisms worth stealing

1. **Multi-source intake with dedupe.** Runlayer, Factory Triage and Devin auto-triage all do this. Merge new asks into existing work and attach the requester as "one more voice".
2. **Point-and-say feedback on running software.** Agentation, ChatGPT browser annotations and Copilot Studio canvas annotation all capture selector, component and note, send them to a webhook, and let the agent resolve the annotation in the same thread.
3. **Risk-tiered routing with explicit always-human zones.** Runlayer's auth and hot-path rule; Devin Autoapprover's rubric plus *exclusions take precedence*; Osmani's "decide per loop".
4. **Evidence instead of diffs.** Devin's annotated test video, Cursor's video artifacts plus remote-desktop takeover, Factory's `/demo` with a script approved before recording, Antigravity artifacts. Non-technical approvers watch rather than read.
5. **Review that verifies its own findings.** Claude Code Review's verification pass; Devin custom reviewers attributed to a named concern.
6. **Bounded babysitting loops.** Agents answer comments and fix CI, capped (Stripe: two CI rounds) with escalation.
7. **Feedback-promoted rules.** Bugbot's candidate, promote, disable lifecycle; Devin memory entries that link to their source session and are compacted nightly; Devin turning a successful test into a committed skill.
8. **Set the governance boundary once, inherit it everywhere.** Databricks App Spaces, Microsoft CMR tenant defaults, Retool permissions on data sources, Runlayer's launcher-scoped agents, Snowflake's active-role execution, Palantir's branch proposals.
9. **Spec as files with derived tests.** Kiro's requirements/design/tasks, EARS notation, property tests from acceptance criteria, plus a *Quick Spec* lane for small work.
10. **Lifecycle hygiene.** Lovable's pre-publish scan, owner and expiry, abandoned-app cleanup, per-app trust page.
11. **Readiness scoring before delegation.** Factory Agent Readiness for brownfield repos.
12. **Enablement as a product surface.** Runlayer's changelog ledger, stakeholder DMs and weekly video digest; Factory's SDLC coverage dashboard.
13. **One assistant, not a cast.** Uber's single assistant, Microsoft Cowork, Runlayer agents in Slack. Users see outcomes, not which agent did what. This matches UA's early feedback.

## 6. Moat analysis: what generic platforms structurally cannot do for UA

**The honest threat.** **Microsoft Copilot Managed Runtime** is the most direct competitor. It is M365-native, uses Entra, inherits tenant policy, gives admins an inventory, and has an app builder for business users that plans and asks follow-ups. For a "build me a tracker on SharePoint data" request, HyperDelivery should not try to beat it. Snowflake and Databricks own the governed data plane, and their builders already know the semantic layer. Lovable, Bolt and v0 out-prototype anything UA will build, and Bolt is moving into Teams.

**What none of them can do, structurally:**

1. **Capture context across functions.** Every generic builder is a single-user chat (Replit shows who asked for what, but nothing more). The UA ideathon finding was that the best context comes from technical and non-technical people *together*. A multi-party Distill session that attributes and cites statements to named stakeholders, and pulls in Teams meeting transcripts the way Runlayer pulls Fireflies, is something no tenant-agnostic vendor will tailor to UA's departments.
2. **Keep institutional memory at the organization level.** Devin's memory is explicitly *personal*. Microsoft, Lovable and others keep context per app or per user. HyperDelivery's decision trail is the raw material for organizational memory that compounds: approved specs, blueprints, gate decisions with signer and reason, review gaps, demo outcomes. Uses include dedupe across EDM and other departments, reuse of prior blueprints, and rules promoted from rejection reasons. Only an internal line sees every project.
3. **Golden paths that belong to UA.** Generic tools ship generic defaults (Devin scaffolds Vite + Tailwind + shadcn by default). HyperDelivery can encode UA's approved stacks, the UA design system, AWS account patterns, Entra app registrations, Snowflake role conventions and data contracts. It can also hand off to engineering through Jira and Confluence in the format UA engineering already reviews.
4. **Governed data access with UA semantics.** CMR governs *connectors*. Snowflake governs *roles*. Neither knows that a given EDM data product may be prototyped against a masked clone but never written back. HyperDelivery can bind each project to a scoped Snowflake role and synthetic or cloned data (StrongDM's digital-twin idea, applied to data).
5. **An accountability chain from intent to evidence.** Spec, then plan, then build, then gap report, then demo, each signed by an Entra identity. Citizen builders produce apps, not decisions. Engineering factories assume an engineer wrote the ticket. HyperDelivery owns the step *before* the ticket and the proof *after* the build. That is exactly what 8090 sells to EY-style buyers.
6. **Neutrality across runtimes.** Each vendor pushes its own runtime. HyperDelivery can publish to whichever runtime fits: CMR for M365-centric tools, Streamlit in Snowflake or Databricks Apps for data apps, AWS for brownfield. The line is the product. Platform churn (Power Apps vibe retired within about a year) is a strong argument for not tying UA users to one vendor's builder.

**What HyperDelivery should not try to be:** another app runtime, a general MCP control plane (buy something like Runlayer, or use AgentCore Gateway), or a dark factory. Its moat erodes wherever it duplicates a commodity layer.
