# GitHub Next Chopin and the GitHub spec/plan lineage: lessons for HyperDelivery

Research date: 2026-10-25. Primary sources: the Chopin repo (cloned at commit `73dbcf3`, 2026-10-25), the GitHub Next project page, GitHub changelogs and docs, and the Spec Kit and gh-aw repos (both cloned). GitHub Universe 2026 is on Oct 28-29, so announcements from it are not covered here.

## 1. Chopin in one paragraph

[Chopin](https://githubnext.com/projects/chopin/) is a GitHub Next **research prototype** published in September 2026 by Krzysztof Cieślak and Maggie Appleton. It is a real-time, multiplayer planning environment where a team and a repository-grounded agent write a durable document together. That document can be an implementation plan, spec, RFC, proposal or decision record. The page argues that coding agents have made implementation cheap, so planning and review are now the bottleneck. It names four failures of current planning tools: plans are static text, the tools are single-player, nobody can tell who decided what, and agents write walls of prose instead of visuals. Chopin is described as the "spiritual successor" to **Ace**, a more ambitious multiplayer agent workspace that is now paused. The [repo](https://github.com/githubnext/chopin) is MIT-licensed, about 480 stars, created July 2026, and pushed to daily (CLI v0.0.21 shipped 2026-10-22). It warns that it is not a supported product: there is no public instance, so you self-host it, and alpha users were expected about a month after the September post.

## 2. Interaction model

Chopin's container is a **channel** bound to one GitHub repository. It has three surfaces ([README](https://github.com/githubnext/chopin/blob/main/README.md), [architecture.md](https://github.com/githubnext/chopin/blob/main/docs/architecture.md)):

- **Chat**, shared by the team and the hosted agent, called the **Planner**. `@chopin` (or a Chat/Chopin toggle on Shift+Tab) addresses the agent. Recent chat enters the agent's context even when nobody addressed it. Chopin also joins in on its own ([conversation-initiative.md](https://github.com/githubnext/chopin/blob/main/docs/conversation-initiative.md)). When one person is talking, it replies after a 1.5 s window. When several people are talking, a small classifier decides whether they invited Chopin or are talking to each other, and Chopin otherwise yields for 15 s of silence. Typing postpones its turn, and only human messages can trigger one, so agent text never triggers more agent text.
- **Document**, labeled "Plan" in the UI. This is a multiplayer WYSIWYG editor backed by a **restricted MDX dialect**: imports, expressions, raw HTML and unknown JSX are rejected, and nothing is ever evaluated. People and the agent edit the same artifact with presence, cursors and transient "change marks" on recent agent edits. Comment threads can go anywhere, and the agent can resolve them.
- **Decisions**, which are attributed records kept **outside the prose**. In the README's words, this is so "a later rewrite cannot silently change what the team decided."

The default Planner is read-only on GitHub: it can read files, search, and inspect history and PRs, but cannot write code. Implementation is handed to a separate coding agent over **MCP** or via a local **ACP** connector (the `chopin` CLI pairs your machine and runs Copilot CLI or another ACP agent).

## 3. How intent, specs and plans are represented

**One document, three forms.** Chopin stores a document as Lexical (for editing), Yjs (a CRDT, for live collaboration) and canonical MDX (a readable durable projection). The server holds the authoritative Y.Doc plus a headless Lexical mirror, validates every batch, and rebuilds from the last good state if a batch breaks the document ([architecture.md](https://github.com/githubnext/chopin/blob/main/docs/architecture.md)). The agent does not send text patches. Its `edit_plan` tool sends **structural block operations** against a specific `planRevision`, and the server checks them before committing. Because of that, the agent preserves human cursors, undo history and provenance.

**Decisions are first-class records** ([decisions.md](https://github.com/githubnext/chopin/blob/main/docs/decisions.md)):
- A decision can be **written** (free text) or **choice** (options). It can be open before anyone knows the alternatives.
- The Planner's `open_decisions` tool creates up to 10 cards in one batch. Each card is **anchored beside the passage it informs**, using a Yjs relative position plus a digest of the block. If an anchor becomes ambiguous, the card is orphaned rather than guessed.
- Only a person's **Save** settles a decision. The docs say a draft, a recommendation, or casual agreement in chat does not. A save records who saved it and queues a scoped rewrite of the linked prose. Several saves in a row are batched into one agent turn after a 5 s quiet window.
- **Reopen** keeps the full answer history. **Discard** preserves it too. The question text is frozen, so reconsidering an answer cannot quietly reword the question.
- A settled decision gets a one-sentence **why** that the agent drafts. A human's wording always beats a later draft.
- **Criteria matrix:** a choice decision can carry up to 5 criteria, and each option is marked yes, partly or no per criterion. The agent may *propose* criteria but **may not mark cells**. The docs treat a mark as a human judgment.
- **Exploring a decision:** a Research menu offers *Research the web*, *Investigate the codebase* (runs on your paired machine) and **Ask someone**. Ask someone routes the question to a named teammate, whose reply ("take") carries a supports/objects stance. Findings attach to the decision record. A decision can expand into its own child page with Findings, Takes and Notes.

**Research as child documents.** `/research` puts an inline progress card in the document. A public worker gets *only the brief* and has web search. Two isolated private workers, with no web access, analyze the document and then write the report. A completed report is published atomically as a child document. Failed or canceled requests never appear in navigation ([architecture.md](https://github.com/githubnext/chopin/blob/main/docs/architecture.md)).

**Plans become task graphs** ([implementation-lifecycle.md](https://github.com/githubnext/chopin/blob/main/docs/implementation-lifecycle.md)). The Planner drafts a versioned dependency graph of tasks with acceptance criteria. The graph is pinned to one `planRevision` and tracked with its own `graphVersion` and `graphRevision`. A person approves it. A coding agent then claims it with `start_implementation` and reports progress with `start_task`, `block_task`, `report_pr`, `complete_task` (including a `noChange` completion that requires a reason and evidence) and `report_verification`. A whole-graph review must pass before the run is released. A scope change ends the run with `request_revision`. An active run locks plan edits that would invalidate the graph.

## 4. How humans steer

- **The Build gate is "inert with a reason."** **Build plan** in the header stays visible but does nothing while the document is empty or has open decisions, accepted comments or required investigations. Its tooltip names what is waiting, and pressing it reveals the blocking card. The docs say plainly: "A completeness score cannot disable Build" ([implementation-lifecycle.md](https://github.com/githubnext/chopin/blob/main/docs/implementation-lifecycle.md)).
- **The press is the approval.** Approval binds the exact document revision, graph revision, checkout commit, connection and person in one durable commit. The Planner's prompt forbids it from approving, locking or starting implementation: "those are decisions and actions for people" ([planner.ts](https://github.com/githubnext/chopin/blob/main/apps/server/src/agent/planner.ts)).
- **After a build, the system shows what changed.** Later edits show up as **"N changes to build"**, counted as top-level blocks added, removed or changed since the last built source. One press rebuilds those changes onto the existing PRs.
- **Questions go on cards, not in chat.** The Planner's coaching prompt says every request for human input must go through anchored decision cards, and never as chat text like "let me know" ([coaching.ts](https://github.com/githubnext/chopin/blob/main/apps/server/src/agent/coaching.ts)). It also tells the agent to "make grounded progress visible early" with a small provisional passage, not to produce "a complete specification from sparse intent," and not to "manufacture consensus."
- **Stop Planner / Stop build** controls, and per-person ownership of local execution: work only runs on the machine of the person who started it.

## 5. UI ideas worth noting

- **Progress derived from real events, in plain language** ([agent-work-progression-design.md](https://github.com/githubnext/chopin/blob/main/docs/agent-work-progression-design.md)). One stable row shows the current phase: *Getting oriented → Gathering context → Waiting for an answer → Making changes → Writing a response → Reviewing the next step*. Each phase maps from real tool events. There is no auto-advancing, no percentage, and no generated reasoning text. The finished row collapses to "4 actions". Tool input and results are available but **collapsed by default**.
- **A status capsule in the header slot:** *Breaking into tasks… / Building 3 of 8 / Built / N changes to build / Build stopped — Retry*.
- **Low-fidelity wireframe DSL.** A `wireframe` code fence (header, nav, card, grid, button and similar) lets the agent sketch UI "the shape, not the copy." It explicitly bans ASCII art. Native **SeeCode** JSON diagrams are preferred over Mermaid. An eval rubric scores whether a visual actually helps the reader ([evals/planner-visual/rubric.md](https://github.com/githubnext/chopin/blob/main/evals/planner-visual/rubric.md)).
- **Resolved cards look like the card people answered**, not a grey summary ([resolved-decision-card-design.md](https://github.com/githubnext/chopin/blob/main/docs/resolved-decision-card-design.md)). The design language is "a working document": white paper, serif headings, calm controls ([DESIGN.md](https://github.com/githubnext/chopin/blob/main/apps/web/DESIGN.md)).
- Phone read mode, a PWA, and demo collaborators ("Lily", "Felix") so one person can rehearse the multiplayer flow.

## 6. Status, limits and early user feedback

GitHub.com only, with no GHES support. GitHub App identity. The default harness needs a **Copilot entitlement**, and the first eligible user's token "owns" the channel's model usage. A channel is bound to a single repository. It runs as a single writer process on PostgreSQL. The approval UI for MCP-created graphs is still incomplete. Issues filed after early use (2026-10-14) are telling:
- [#597](https://github.com/githubnext/chopin/issues/597): users read "decision" as *already decided* and didn't know decisions could be open or created by hand.
- [#596](https://github.com/githubnext/chopin/issues/596): with two people prompting at once, users couldn't tell *which agent edit answered which request*.
- [#595](https://github.com/githubnext/chopin/issues/595): users want documents that span several repositories.

**The arc:** GitHub keeps moving the human's steering point *earlier* (from diff, to plan, to spec, to a shared decision) and *more social* (from a single-player snapshot, to a shared canvas, to multiplayer decisions). It has repeatedly retreated from building a separate non-developer app builder (Spark).

## 8. Patterns HyperDelivery should borrow

1. **Keep decisions apart from the spec text.** HyperDelivery's `OpenQuestion` (`src/core/domain/project.py`) already has options and multi-select. Extend it into a Decision record: status (Open, Exploring, Waiting on a person, Settled), `saved_by` and `saved_at`, anchors to requirement IDs, answer history kept on Reopen, a frozen question, and a one-line why. Regenerating Distill or Blueprint output must not be able to change a settled decision.
2. **Make the approval button "inert with a reason."** Today `_has_open_gaps` holds a project at its station. Keep the Approve button visible, but disable it while decisions or comments are open, show what is waiting, and jump to the blocking card when pressed. Show the completeness score as advice, not as a gate.
3. **Questions go on cards, never in chat.** Add Chopin's rule to the Distill and Blueprint prompts. Also tell them to draft a small provisional section first and then ask everything they need in one batch.
4. **Progress in plain language, derived from real events.** This answers the feedback that users don't care which agent is doing what. Show one phrase from real events ("Reading your Confluence page", "Drafting the spec", "Waiting for your answer", "Building 3 of 8") with technical detail collapsed. No percentages, no fake reasoning text, and no agent names in the main view.
5. **One living project document.** Each station adds a section (what we heard, how it works, what's being built, the demo) instead of handing off four separate artifacts. The crew personas can be secondary flavor.
6. **"Ask someone."** Route a decision to a named colleague through Teams and record their reply with a supports/objects stance. This is the cheapest way to get the ideathon's cross-functional effect.
7. **Bind each approval to an exact revision, and show "N changes since approval."** Store the artifact hash with the Step Functions task token. Then re-approval after a change only asks people to review the delta.
8. **Low-fidelity wireframes and native diagrams in specs.** Non-technical stakeholders react to shapes faster than to "FR-001" requirement lists.
9. **Research as a separate child item with isolated workers.** The web-search worker sees only the brief, and private context never reaches the web.
10. **Assess before Distill** (borrowed from Spec Kit's assess extension): end with a go / needs-clarification / kill verdict and a human gate. This fits ideation-heavy business users.
11. **gh-aw guardrails for side-effecting tools:** staged previews for repo creation and Jira filing, a write path separate from the agent, and **cost per accepted outcome**, which builds on the Bedrock cost tracking you just added.
12. **Traceability links**, like `Agent-Logs-Url`: put a link back to the HyperDelivery project timeline in Copilot coding agent issues and commits, and pass acceptance criteria as structured fields (Copilot for Jira already reads them).

## 9. What to avoid

- **Copilot Workspace's file-level plan as the user-facing artifact.** A list of files to edit means nothing to business users. Its "edit upstream, everything downstream regenerates" model also erased context, and its snapshot sharing was single-player.
- **Building a separate non-developer app runtime on someone else's preview service.** Spark was deprecated, and its `llm()` calls broke when GitHub Models retired. Keep runtime and inference on AWS (AgentCore and Bedrock) and keep exports possible.
- **Gating on a completeness score or showing percent-complete.** Chopin rejects both on purpose.
- **Confusing labels.** "Decision" was misread as "already decided" (#597). Test the names you show users with real UA business users.
- **Tying a project to one repository.** Chopin's users already pushed back (#595), and brownfield UA work will touch Snowflake, several repos and Jira.
- **An agent that joins chat uninvited with no off switch.** Chopin removed its pause control. For enterprise rollout, keep agents opt-in in group spaces.
- **Copying Chopin's machinery.** It has many separate counters, a single-writer Postgres design, and GitHub identity throughout. HyperDelivery needs Entra ID, M365 surfaces (Teams and Loop), and a lighter way to collaborate before it needs full CRDT editing.
- **Agents with read access to untrusted text and also write tools.** gh-aw's prompt-injection report is the warning. Keep side effects behind human gates and validated writes.
